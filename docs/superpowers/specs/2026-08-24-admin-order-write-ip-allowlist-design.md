# 后台订单写操作 IP 白名单设计

## 1. 背景与目标

后台认证目前存在可预测令牌和兼容请求头可参与账号解析的问题。攻击者即使不再访问后台页面，也可能直接调用订单管理接口修改还款状态。仅修改后台密码、创建新账号或限制后台域名都不能立即阻断这类请求。

本次目标是在商城持续运行的前提下，只允许指定公网 IP 执行后台订单写操作，并为后续修复后台认证保留清晰边界。

生产环境首个允许地址由部署配置提供，当前确认值为 `129.227.151.105/32`。该值不得硬编码到业务源文件。

## 2. 范围

### 2.1 本次保护的操作

保护所有带订单 ID 的后台订单写请求：

- `PATCH /api/orders/{orderId}/...`
- `DELETE /api/orders/{orderId}`

这组路径覆盖人工标记已还或未还、全款支付标记、延期或修改还款日、协商还款、协商结清、协商记录状态修改、订单状态修改、物流登记、卡包状态修改、合同状态修改和订单删除。

### 2.2 必须保持开放的商城业务

下列请求不受后台订单写白名单影响：

- `POST /api/orders`：商城用户下单；
- `GET /api/orders...`：订单查询；
- `/api/auth/...`：商城注册和登录；
- `/api/bills/...`：商城账单和用户还款；
- `/api/payment/...`：支付预下单、状态同步和支付回调；
- 商品、地址、银行卡、合同确认、客服和流量渠道的既有商城接口。

本次不修改订单、账单、支付流水或用户数据，不执行数据库迁移。

## 3. 推荐方案

采用 Nginx 边缘限制和 API 应用限制两道独立防线。任意一道配置遗漏时，另一道仍能阻止非白名单来源修改订单。

### 3.1 Nginx 紧急防线

在 Nginx `http` 级别读取独立的可信 IP 配置文件，并计算当前请求是否来自可信来源。生产 IP 只写入服务器本地配置，不提交到业务代码。

所有可到达 API 的入口都必须应用同一个订单写保护条件：

- 商城 HTTPS 域名的 `/api/`；
- 默认 HTTP/IP 入口的 `/api/`；
- 后台备用端口 `8080` 的 `/api/`；
- 流量后台端口 `8081` 的 `/api/`。

当请求同时满足以下条件时，非可信 IP 返回 `403`：

1. 方法是 `PATCH` 或 `DELETE`；
2. 路径以 `/api/orders/` 开头。

后台页面 `admin.wenshuosc.com` 和备用后台页面端口 `8080` 也只允许可信 IP 访问。证书验证路径 `/.well-known/acme-challenge/` 保持开放，避免影响证书续期。

Nginx 使用直接连接来源地址做判断。若以后接入 CDN 或负载均衡，必须先配置可信代理地址，再从代理头恢复真实客户端 IP；不得直接信任任意客户端提交的 `X-Forwarded-For`。

### 3.2 API 应用防线

新增独立安全模块，职责仅包括：

- 从环境变量 `ADMIN_ORDER_WRITE_ALLOWED_IPS` 读取允许的单个或多个 IP；
- 判断请求是否属于受保护的订单写操作；
- 安全解析来源 IP；
- 对非白名单请求返回 `403`，对配置缺失返回仅影响敏感写接口的 `503`；
- 记录允许、拒绝和配置错误事件，不记录 Authorization、密码或完整请求体。

来源 IP 的信任规则为：

1. Node 连接来源不是本机回环地址时，只使用 socket 来源地址，忽略客户端伪造的转发头；
2. Node 连接来源是本机 Nginx 时，读取由 Nginx 覆盖设置的 `X-Real-IP`；
3. 统一处理 IPv4、IPv4-mapped IPv6 和 IPv6 文本形式；
4. 不允许通过查询参数或业务请求体传入白名单 IP。

该中间件必须在订单路由执行前运行，但不能拦截商城公开接口。生产环境未配置白名单时仅将受保护的后台订单写接口设为失败关闭，商城其他接口继续服务。

### 3.3 后续认证修复

IP 白名单完成止血后，继续进行后台认证修复：

- 后台登录签发高熵随机会话令牌；
- 会话具有过期时间、服务端存储和主动撤销能力；
- 移除通过手机号、角色请求头或查询参数直接取得后台身份的兼容路径；
- 强制所有后台账号重新登录并轮换密码；
- 为还款及其他敏感操作记录操作者、来源 IP、时间、目标订单、期数和修改前后状态。

认证修复不得改变商城用户当前登录和支付回调契约，应拆分为后续独立上线步骤。

## 4. 请求处理流程

1. 客户端请求先到 Nginx。
2. Nginx 对后台页面和后台订单写路径执行可信 IP 判断。
3. 非可信来源立即得到 `403`，请求不会到达 Node。
4. 可信来源被代理到 API。
5. API 中间件重新识别受保护路径和来源 IP。
6. API 白名单通过后才进入现有 RBAC 和订单业务逻辑。
7. 现有权限检查仍然保留，IP 白名单不能代替账号权限。

## 5. 配置与失败策略

- 服务器本地 Nginx 可信 IP 文件保存 `129.227.151.105/32`；需要更换 IP 时只修改该文件并执行 `nginx -t` 后 reload。
- API 生产环境设置 `ADMIN_ORDER_WRITE_ALLOWED_IPS=129.227.151.105`；支持逗号分隔多个紧急地址。
- Nginx 配置无效时不得 reload，继续使用上一份有效配置。
- API 白名单缺失或格式错误时，商城继续运行，但后台订单写请求返回 `503` 并写安全日志。
- 白名单用户 IP 变化时会暂时无法操作后台订单，但不影响商城用户。

## 6. 验证方案

### 6.1 自动化验证

为 API 安全模块增加测试，至少覆盖：

- 白名单 IPv4 可以执行受保护请求；
- 非白名单 IPv4 返回 `403`；
- 回环 Nginx 连接正确读取 `X-Real-IP`；
- 非回环直连不能用伪造 `X-Real-IP` 绕过；
- IPv4-mapped IPv6 正确归一化；
- `POST /api/orders` 不受限制；
- `GET /api/orders...` 不受限制；
- `/api/bills/...` 和 `/api/payment/...` 不受限制；
- 白名单缺失时只有受保护写接口返回 `503`。

### 6.2 上线验证

1. 备份当前 Nginx 配置和相关访问日志。
2. 执行 `nginx -t`，只有通过后才 reload。
3. 从白名单 IP 登录后台并测试一条不改变业务数据的权限检查或预检请求。
4. 从非白名单网络确认后台页面和受保护写接口返回 `403`。
5. 验证商城登录、商品查询、订单查询、下单预检、账单查询和支付回调路由仍可访问。
6. 检查 Nginx 与 API 安全日志，确认来源 IP 解析一致。
7. 从项目根目录执行 `node scripts/check-mojibake.js .`。

任何验证不得为了测试而修改真实还款状态。需要验证实际写入时，只能使用明确标记的测试订单，并由用户单独授权。

## 7. 回滚

- Nginx reload 前保留原配置副本；发生异常时恢复副本、执行 `nginx -t` 后 reload。
- API 修改保持为独立安全模块和独立中间件挂载；回滚代码不会触碰业务数据。
- 回滚 IP 限制不等于解决认证漏洞。若必须临时回滚，应暂停后台订单操作并优先恢复安全配置。

## 8. 风险与边界

- 固定公网 IP 变化会导致合法管理员被拒绝，需要通过服务器控制台更新白名单。
- 仅限制后台页面不能阻止直接 API 调用，因此订单写路径保护是必要条件。
- IP 白名单能立即阻断当前远程攻击，但不能替代随机会话、密码轮换和审计日志。
- 若服务器本身或白名单网络已被控制，IP 白名单无法提供完整保护，需要进一步进行主机取证和密钥轮换。
