# API Mongo 读取一致性、性能与支付落库安全修复设计

## 目标

修复 admin 后台和 shop 前台同时出现的接口卡顿、HTTP 200 但业务数据为空、刷新后数据偶尔恢复，以及客户完成支付后订单仍显示未还款、后台没有还款记录的问题。

本次只修复 API 进程内缓存刷新、Mongo 持久化结果传播和拉卡拉支付完成流程。不得连接、迁移、补写、删除、重置或批量修正任何线上业务数据；不得自动处理历史异常支付。用户完成代码部署后，历史异常只通过只读核对清单单独排查。

## 已确认根因

### 冷启动局部快照被误认为完整快照

`store.js` 允许部分接口在没有内存快照时只加载 1 至 5 个集合。未加载集合会被初始化为空数组，但当前实现仅在加载集合数不超过 1 时标记快照不完整。`MONGO_REFRESH_MODE=version` 随后可能把该快照误认为完整并跳过 Mongo 读取。

这会让 Mongo 中实际存在的 `lakalaPayments`、地址、银行卡或其它集合在内存中表现为空，并由接口正常包装成 HTTP 200 空数据。拉卡拉通知命中这种快照时还会把真实支付单当成未知支付单。

### 全量刷新失败会先丢弃最后一份有效快照

全量刷新开始前会删除当前 scope 的内存快照。若任一集合读取失败，GET 中间件会吞掉异常并继续执行，`readDb()` 随后返回空种子数据。这正好形成“Mongo 短暂抖动 -> HTTP 200 空数组 -> 多次刷新后恢复”的故障链。

### 刷新队列重复读取且缺省配置会退化

同一 scope 的并发刷新当前被逐个追加到队列，而不是复用正在执行的相同刷新。因此页面并发请求可能重复读取相同集合。`MONGO_REFRESH_MODE` 缺失或非法时，代码还会返回空模式，实际效果接近每个请求都全量读取 13 个集合。

### Mongo 持久化失败被吞掉

持久化队列捕获 Mongo 异常后只记录日志，不向调用方 reject。支付服务等待 `flushMongoPersist()` 后仍会认为落库成功，向商城或拉卡拉返回成功。刷新或进程重启后，只有内存中存在的已还状态会消失。

### 支付完成状态设置顺序破坏重试语义

支付流水当前先被标记为 `success`，之后才查找订单并应用还款。若业务应用或持久化在中途失败，同进程内下一次回调会因为 `status === success` 直接返回，不能继续完成订单入账。

## 安全边界

- 不运行任何连接生产 Mongo 的写命令、迁移脚本、修复脚本或数据回填脚本。
- 不通过本任务执行任何脱离正常 API 业务请求的数据修改；新支付通知仍只更新它本来就应更新的对应订单和支付流水。
- 不新增必须对历史文档执行迁移的字段或索引。
- 不改变正常成功请求的响应数据结构。
- 本期不修改 admin 和 shop 前端文件；若后续验证发现独立前端缺陷，必须另行说明并确认范围。
- 不修改拉卡拉金额计算、还款金额、分期规则、订单归属规则或支付渠道配置。
- 所有测试使用本地内存桩或测试夹具，不访问线上环境。
- 不自动补偿历史异常支付；历史记录只能在部署后按订单号、支付流水号进行只读核对，再由业务负责人单独决定处理方式。

## 方案概览

采用“最后有效快照 + 按集合版本覆盖 + 可观察降级 + 可传播持久化结果”的方案，不进行全量 repository 重写。

```text
请求刷新
  -> 根据路由计算所需集合和是否必须使用新鲜数据
  -> 检查这些集合各自对应的 app_meta 版本
  -> 复用相同的进行中刷新，或只加载缺失/过期集合
  -> 所有读取成功后一次性发布新快照
  -> 读取失败时保留最后有效快照
       -> 所需集合已有旧快照：只读接口返回旧数据并标记 stale
       -> 所需集合从未加载：返回 503，不再返回 200 空数据
       -> 写请求或有副作用的 GET：始终返回 503
```

支付写入流程：

```text
收到已支付结果
  -> 定位本地支付流水；找不到则返回 FAIL 让支付方重试
  -> 校验关联用户、订单和期次
  -> 应用可重复执行的还款操作
  -> 等待 orders + lakalaPayments 当前持久化任务真实完成
  -> 只有 Mongo 确认成功后才返回支付成功/回调 SUCCESS
  -> 任一步失败均返回失败，不吞异常；后续通知可继续重试
```

## 快照完整性与版本模型

用每个 scope 的“集合版本覆盖”替代当前单一的 `mongoScopeHydrateIncomplete` 布尔集合：

- 每个 scope 记录各实体集合最后成功加载时对应的 `app_meta.updatedAt`。
- 每个 scope 同时记录正在持久化或最近持久化失败的实体集合；这些集合在重新持久化或重新从 Mongo 加载成功前不得作为 stale 快照使用。
- 冷启动 partial 只登记本次确实成功加载的集合；未加载集合没有版本，不能被当成空数据。
- partial 刷新只更新本次集合的版本，不把其它集合误标成最新。
- full 刷新只有在全部实体集合读取、解析和元数据同步成功后，才一次性发布快照并把所有集合登记为同一版本。
- `version` 模式只有在当前路由所需的每个集合版本都等于 Mongo 当前版本时才允许跳过。
- `every_request` 保持强制刷新语义；`single_instance` 也必须先确认所需集合已实际加载。
- 删除 tenant 缓存时同步删除其集合版本信息。

全量和局部 hydrate 都必须先构造候选快照，成功后再替换 `mongoMemoryDbByTenant`。失败时不得清除或部分覆盖最后有效快照。

## 并发刷新与性能

- 同一 scope、相同集合签名的并发刷新共享同一个进行中 Promise，只执行一次 Mongo 读取。
- 不同集合签名继续按 scope 串行合并，避免两个 partial 快照互相覆盖。
- 等待前序刷新后再次检查集合版本，已经被前序刷新覆盖的集合不重复读取。
- refresh 在读取 Mongo 前等待同 scope 已经排队的持久化任务，避免并发 GET 从 Mongo 拉回旧值并覆盖尚未完成的本地写入。
- `MONGO_REFRESH_MODE` 缺失或非法时按文档约定回落到 `version`，不再退化成每请求全量刷新。
- `/api/payment/lakala/config` 等完全不依赖业务快照的接口使用 `skip`。
- `/api/admin/orders/repayment-records` 只加载生成还款记录所需的支付流水、用户、订单和渠道相关集合。
- shop 账单、订单、支付状态等接口只加载其实际依赖集合；所有写请求仍必须在执行业务前获得足够且新鲜的数据。
- 支付预下单的最小集合为 `products/users/orders/lakalaPayments`；支付通知、状态同步、pending 同步和模拟完成的最小集合为 `users/orders/lakalaPayments`。这些路径全部使用 strict freshness。其它未逐条审计的非 GET 保持 full，不做激进轻量化。
- 后台账号跨库鉴权本期不改变安全语义，不为性能取消账号状态实时校验。

## 刷新失败处理

刷新策略必须同时携带以下信息：

- `mode`: `skip`、`partial` 或 `full`。
- `keys`: 当前 handler 实际需要的实体集合。
- `requiresFresh`: 是否可能写业务数据或产生支付副作用。

失败行为固定为：

- 普通只读接口且所需集合都有最后有效快照：继续返回最后有效数据，设置 `X-Data-Stale: 1`，并输出不含手机号、支付报文等敏感数据的 warning 日志。
- 普通只读接口但缺少任一所需集合：返回 503 和标准失败结构，handler 不得继续执行。
- POST、PUT、PATCH、DELETE：刷新失败一律返回 503。
- 所有会落库或触发外部副作用的 GET 都必须按 `requiresFresh: true` 处理，刷新失败时不得使用旧快照继续。已确认至少包括支付状态同步、合同查看/签约、商城与后台客服已读、可能更新黑名单的订单查询，以及会写审计记录的 platform 查询。
- `skip` 路由的直连 Mongo helper 必须区分“不适用优化”和“数据库查询失败”：只有前者可以走原逻辑；查询失败必须向上抛出。普通只读路由只有在其 `keys` 对应的有效快照已存在时才允许 stale fallback，否则返回 503，禁止退回空 seed。该规则覆盖商品列表、后台账号、订单分页和侧栏数量等现有直查路径。

旧快照降级仅用于短暂读取可用性，不向 Mongo 回写，也不触发任何业务数据修改。

## 持久化队列语义

持久化队列拆分为两个 Promise 概念：

- 队列 tail 捕获上一任务错误后继续执行，保证一次失败不会永久毒化该 scope 的后续写入。
- 当前任务结果保留原始 reject，`writeDb`、`writeDbPartial`、`writeDbEntity` 和 `flushMongoPersist` 的调用方能够感知真实失败。

partial 持久化使用调用时捕获的不可变快照，不在任务真正执行时重新读取可能已被 refresh 替换的共享内存。FIFO 顺序保证后调度的快照最后写入，避免旧 Mongo refresh 快照覆盖已经应用的还款状态。

支付完成不再用整个 `orders` 和 `lakalaPayments` 数组执行集合级快照替换。新增同一 scope 队列内的“精确实体批量持久化”能力，只按 `_id`/业务主键 upsert 当前支付流水及本次确实变化的订单，并在全部精确写入后更新一次 `app_meta`。该操作不扫描删除其它文档，也不会因为局部内存快照缺集合而清空业务数据。

精确实体批量持久化在调度时深拷贝并按“实体集合 + 主键”去重，只执行 `replaceOne(..., { upsert: true })`，不调用 `find`、`deleteMany` 或整集合 `bulkWrite`。只有 Mongo 写入全部成功后，才把对应实体合并回当前内存快照。失败时内存继续保留最后已确认持久化的实体。

通用写入若因现有同步 API 必须先更新内存，则把受影响集合标记为 pending/dirty：成功后清除标记；失败后保持不可降级状态，并在下一次请求强制从 Mongo 恢复。这样未持久化的“内存已还款”不会作为旧快照返回给页面。

通用请求末尾等待持久化失败时必须记录错误；支付相关路径必须在自己的业务函数内显式等待并传播错误，不能只依赖响应结束后的通用 flush。

## 支付完成与重试

- 创建支付单时，本地 pending 流水必须成功持久化后才向客户端返回可支付地址。Mongo 写失败时接口返回失败，不把无法追踪的收银台地址交给客户。
- 在调用拉卡拉创建外部订单前先持久化本地 pending 流水，确保任何可能到达的支付通知都有可查询的本地业务主键；外部调用结果再精确更新同一流水。
- 成功通知处理前先校验支付流水、用户、订单和期次，不在校验完成前设置 `success`。
- 还款应用函数必须保持幂等：已经支付的订单或期次再次执行不得重复计费，也不得破坏现有状态。
- 四种业务类型分别定义完成断言：整单支付检查目标订单；普通分期检查指定期次；协商支付同时检查协商待支付标记和已支付历史；一键还款检查本次业务函数实际触及的订单。业务函数必须返回本次真正变化的订单列表，不能把全部订单交给持久化层。
- 新创建的一键还款流水在计算客户确认金额时同时保存该次付款对应的订单/期次目标，回调和重试只能处理这组目标，不能把重试期间新出现的待还账单一并结清。该可选字段只随新流水写入；历史流水不迁移、不批量补字段，并保留兼容读取路径。
- `status === success` 只有在关联订单/期次也已经满足对应业务完成条件时才可视为业务上已处理；即便属于重复通知，也必须再次确认本次涉及的精确实体已成功持久化后才能 ACK。这样前一次写失败留下的内存 success 不会让重试直接跳过。
- “流水成功但订单未还”必须继续执行修复性重试，但仅针对当前收到的真实支付通知，不扫描或批量修改历史数据。
- Mongo 持久化失败时，当前请求或回调返回失败；内存状态不得让下一次回调被错误短路。
- 同一 `outTradeNo` 的并发通知共享同一个结算 Promise；第一次失败时所有等待者都返回失败，下一次独立通知才重新尝试，避免并发回调提前 ACK。
- 支付方通知中的未知 `outTradeNo` 不再 ACK `SUCCESS`，而是返回失败并记录流水号，等待合法记录可见后重试。
- 非成功支付状态仍按现有协议记录；本期不猜测或扩展未确认的拉卡拉状态枚举。
- 实际支付渠道补全属于结算后的 best-effort 元数据；补全失败只记录 warning，不撤销已经确认持久化的核心还款，也不把成功结算重新报告为失败。
- 本期不增加回调签名规则，避免在没有支付平台正式验签参数的情况下中断线上回调；验签作为独立安全任务处理。

该设计不依赖 Mongo 事务或新索引，避免部署环境不是副本集时出现兼容问题。一次精确批量写在进程崩溃时仍可能只完成部分文档，但回调不会在已知失败时 ACK，重复通知会幂等地重写同一批精确实体并最终收敛；不会通过全集合替换影响其它订单或支付流水。

## 可观察性

新增日志只记录定位问题所需的非敏感字段：

- refresh 失败的 method、path、workspace、tenant、计划模式、集合名、是否使用旧快照和错误摘要。
- 持久化失败的 workspace/scope、实体集合名和错误摘要。
- 支付回调失败的 `outTradeNo`、业务类型和阶段，不记录完整回调 body、手机号、银行卡或鉴权信息。

正常请求不增加逐请求 info 日志，避免线上日志放大。

## 测试策略

所有行为先按 TDD 写失败测试并确认 RED，再写最小实现并确认 GREEN。

### 快照测试

- 冷 partial 加载多个集合后，未加载集合不被标记为最新。
- 冷 partial 后请求 full，版本相同也必须加载缺失集合。
- 不同集合在同一全局版本变化后的 freshness 分开跟踪，刷新 users 不会把 orders 误标为最新。
- full refresh 中任一集合失败时保留原完整快照。
- partial refresh 失败时不发布半成品快照。
- 持久化 pending/dirty 的集合不能作为旧快照降级，重新从 Mongo 加载成功后才恢复可读。
- 相同 scope 和集合签名的并发刷新只读取一次。
- 不同 partial 顺序执行后，最终快照同时包含两者结果。
- 缺省或非法 `MONGO_REFRESH_MODE` 返回 `version`。

### HTTP 刷新策略测试

- 写请求刷新失败必须阻断。
- 普通 GET 有覆盖所需集合的旧快照时允许 stale 降级。
- 普通 GET 没有所需集合时返回 503。
- 支付状态 GET 标记为 `requiresFresh`，失败时阻断。
- 合同、客服已读、订单黑名单协调和 platform 审计等有副作用的 GET 同样标记为 `requiresFresh`。
- 拉卡拉 config 跳过快照刷新。
- 还款记录、账单和支付状态路由的集合依赖完整且没有多余的全库刷新。
- 商品、后台账号、订单分页和侧栏计数的直连 Mongo 查询失败时，不会在冷启动回退为 HTTP 200 空结果。

### 持久化与支付测试

- 当前持久化任务失败时 `flushMongoPersist()` reject。
- 一次持久化失败后，同 scope 的下一次任务仍能成功执行。
- partial 写入使用调度时快照，而不是执行时被 refresh 替换的快照。
- 支付精确批量写只 upsert 当前流水和实际变化订单，不执行集合删除或整集合替换。
- 支付精确批量写失败时不向内存发布未持久化状态。
- 支付完成只 upsert 当前支付流水和受影响订单，不读取或删除集合中的其它文档。
- pending 支付流水持久化失败时不返回收银台地址。
- 订单应用失败时流水不能提前成为不可重试的 success。
- Mongo 写失败时 notify 返回 FAIL，不能返回 SUCCESS。
- 第一次失败后的第二次回调会重新完成还款。
- 两个并发重复通知共享同一结算；首个写入失败时两个通知都失败，后续独立重试才可成功。
- 未知支付流水返回 FAIL。
- 重复成功通知不会重复修改已经完成的订单或期次。

## 验收标准

- Mongo 中存在数据时，不再因冷 partial 或刷新失败返回 HTTP 200 空种子数据。
- Mongo 短暂失败且已有完整旧快照时，普通只读页面继续显示旧数据，并可从响应头和日志识别 stale。
- Mongo 短暂失败且没有可用快照时明确返回 503。
- 同一页面的并发相同刷新不再重复扫描集合。
- Mongo 持久化失败能够到达支付 API 和拉卡拉通知路由，后者返回 FAIL。
- 支付成功流水不能在订单还款尚未完成时被永久幂等跳过。
- 正常 admin/shop 响应结构、金额和业务判断保持不变。
- 没有任何生产数据迁移、回填、清理或重置操作。

## 部署与回滚边界

用户负责部署。本任务不登录服务器、不修改服务器环境变量、不重启进程、不执行数据库命令。

部署前保留当前应用版本，以代码回滚作为唯一回滚方式。回滚不得恢复、覆盖或删除 Mongo 数据。部署后先检查健康接口和日志，再依次验证商品配置、shop 账单、后台还款记录以及一笔由业务方控制的真实支付流程。

历史异常数据在本次代码部署之外处理。核对时只读取拉卡拉流水、`lakalaPayments` 和订单分期状态，生成差异清单；任何人工补记或状态修正都必须另行确认，不能由本修复自动执行。

## 非目标

- 不重写整个数据访问层，不把全部 handler 改为 Mongo repository 直查。
- 不调整现有订单、分期、还款金额或支付渠道业务规则。
- 不自动修复历史订单或支付流水。
- 不变更生产 Mongo 拓扑、连接池、索引或集合结构。
- 不降低后台登录和账号状态校验安全级别。
- 不在本期实现拉卡拉回调验签或多租户回调 URL 重构。
